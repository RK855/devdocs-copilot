# 限流设计

## 为什么限流

保护系统不被突发流量击穿，防止恶意刷接口，保证资源公平分配。限流是最后一道防线，前面还有鉴权与配额。

## 常见算法

- 固定窗口：按时间窗口计数，实现简单，但窗口边界会出现双倍突发
- 滑动窗口：按更细粒度统计，平滑边界问题，内存开销更大
- 令牌桶：按固定速率补充令牌，允许一定突发
- 漏桶：请求按固定速率流出，平滑流量但不允许突发

对外 API 常用令牌桶，既限制平均速率又允许短时突发。

## 限流维度

按 IP、用户、API key、接口、租户组合。只按 IP 会被 NAT 后的多用户共享误伤，只按用户会被未登录流量绕过。多维度组合更合理。

## 分布式限流

单机限流在多实例下总阈值会翻倍。集中式用 Redis 原子计数或令牌桶脚本；本地限流加全局配额是常见折中。

## 返回与重试

触发限流返回 429，带 `Retry-After` 告知等待时间。客户端应尊重该头并退避，而不是立即重试。

## 配额与计费

AI 调用、短信等有成本的接口常用配额制：按天或按月分配额度，超出后拒绝或降级。配额与限流是不同概念，前者是业务额度，后者是瞬时保护。

## 监控

记录被限流的请求量、维度分布、误伤情况。阈值过严会伤害正常用户，过松则保护无效，需要根据真实流量调整。

## 常见坑

- 只在单机限流
- 所有接口同一阈值
- 限流后不告知重试时间
- 按 IP 限流误伤 NAT 用户
- 阈值写死无法调整
