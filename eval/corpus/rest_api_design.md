# REST API 设计

## 资源与路径

REST 以资源为中心，路径用名词复数，动词交给 HTTP 方法。`GET /users`、`GET /users/1`、`POST /users`、`PATCH /users/1`、`DELETE /users/1`。

避免 `GET /getUserList` 这类 RPC 风格路径，也不要 `POST /users/delete`。确实无法用 CRUD 表达的动作，可以挂子资源，例如 `POST /orders/1/cancel`。

## 层级与嵌套

强归属关系可以嵌套：`GET /users/1/orders`。嵌套层级不要超过两层，过深难维护。跨资源查询用查询参数更清晰：`GET /orders?user_id=1`。

## 查询参数约定

分页用 `page` + `page_size`，或游标 `cursor` + `limit`。排序用 `sort=created_at`，降序 `sort=-created_at`。过滤用字段名直接作参数。复杂过滤可以用 `filter[status]=paid`，但要注意解析复杂度。

响应分页信息放在 `meta` 或响应头，包含总数、下一页游标。列表响应结构要稳定，不要有时返回数组有时返回对象。

## 响应结构

常见两种风格：直接返回资源对象，或包一层 `{"data": ..., "error": null}`。后者便于统一错误处理与扩展元信息，但多一层嵌套。团队内必须统一，不能让前端猜。

错误响应至少包含机器可读的 `code` 与人类可读的 `message`，可选 `details` 数组。不要只返回一句中文，前端无法分支。

## 状态码与语义

创建返回 201 并带 `Location`；删除成功返回 204；校验失败 422；资源不存在 404；权限不足 403。详见状态码文档。

## 幂等与并发

PUT 与 DELETE 应幂等。并发更新用乐观锁：请求带 `version` 或 `If-Match`，版本不匹配返回 409 或 412。这样避免后写覆盖先写。

## 版本管理

破坏性变更必须升版本。新增可选字段、新增接口是兼容变更，不需要升版本。废弃字段要先文档标注，保留一段时间再删除。

## 文档与契约

OpenAPI 是事实标准。FastAPI 自动生成 `/docs` 与 `/openapi.json`。响应模型要显式声明，否则文档与真实返回不一致。契约变更应同步更新前端类型。

## 安全与限流

认证用标准头，不要自定义 `X-Token`。敏感操作要求二次确认或幂等键。限流按用户或 IP，返回 429 与 `Retry-After`。上传接口限制大小与类型。

## 常见反模式

- 动词路径
- 全用 POST
- 列表不分页
- 错误信息只有一段中文
- 返回数据库实体全部字段
- 接口返回 200 但 body 里写 error
- 破坏性变更不升版本直接改字段
