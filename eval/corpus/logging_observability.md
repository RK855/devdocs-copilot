# 日志与可观测性

## 日志级别

DEBUG 用于开发细节，INFO 记录正常关键事件，WARNING 表示可恢复的异常，ERROR 表示功能失败，CRITICAL 表示服务不可用。生产默认 INFO，排障时临时开 DEBUG。级别滥用会让日志失去价值：全是 INFO 等于没有重点。

## 结构化日志

用 JSON 输出而不是拼接字符串，便于检索与聚合。每条日志包含时间、级别、logger 名、消息、请求 id、用户 id、耗时、错误码。

```python
logger.info("retrieval done", extra={"hits": 5, "elapsed_ms": 120, "request_id": rid})
```

字段命名要统一，避免同一含义出现 `user_id`、`uid`、`userId` 三种写法。

## 请求链路追踪

为每个请求生成 request id，放进上下文变量，所有日志自动带上。跨服务调用时通过请求头传递，形成完整链路。没有链路 id 时，并发场景下日志会互相穿插，无法还原一次请求。

## 不要记录的内容

密码、token、Cookie、完整请求体、身份证号、手机号。日志系统往往权限较宽、保留时间长，泄露代价高。需要排查时记录脱敏后的摘要或哈希。

## 异常日志

记录异常要带堆栈：`logger.exception("...")` 会自动附加当前异常。只记录 `str(e)` 会丢失调用栈。同时记录关键上下文（入参摘要、请求 id），否则只有堆栈也难以复现。

## 指标与告警

日志是事后排查，指标是实时观测。常见指标：请求量、错误率、P95/P99 延迟、队列长度、外部依赖可用性。错误率突增与延迟抬升应触发告警。只看平均值会掩盖长尾问题。

## 日志聚合

单机日志文件在分布式环境无法统一检索。生产环境通常输出到 stdout，由采集器送到集中系统。日志轮转要配置大小与保留天数，避免磁盘写满。

## 采样与降噪

高频正常日志可以采样，错误日志不要采样。为日志加固定前缀或事件名，方便过滤。重复错误要做聚合计数，而不是每条都刷屏。

## 常见坑

- 用 print 代替 logger，无法控制级别与输出
- 日志里拼接大对象，拖慢主流程
- 捕获异常后只记录 message，丢失堆栈
- 没有 request id，无法关联
- 日志写本地文件且不轮转
- 在循环里打 DEBUG 日志，生产忘记关闭
