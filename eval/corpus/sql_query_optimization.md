# SQL 查询优化

## 执行计划

优化前先看执行计划。PostgreSQL 用 `EXPLAIN ANALYZE`，MySQL 用 `EXPLAIN`。关注是否走索引、扫描行数、是否出现全表扫描、排序与临时表开销。凭感觉加索引往往无效。

## 索引

B-Tree 索引适合等值与范围查询。联合索引遵循最左前缀原则：`(a, b, c)` 能支持 `a`、`a+b`、`a+b+c`，不能直接支持只查 `b`。把最常用于过滤的列放左边。

索引不是越多越好：每个索引都会增加写入成本与存储。低基数列（如性别、状态只有几个值）单独建索引收益有限。

覆盖索引让查询只读索引不读表，减少回表。把 SELECT 需要的列加入索引可以显著加速。

## 避免索引失效

- 在索引列上做函数运算，如 `WHERE lower(name) = 'x'`
- 隐式类型转换，如字符串列与数字比较
- 前导通配符 `LIKE '%x%'`
- `OR` 连接不同列
- 违反最左前缀

需要函数查询时可以建表达式索引。

## 减少数据量

只 SELECT 需要的列，避免 `SELECT *`。分页优先游标而非大 offset。聚合前先过滤，别把全表拉进内存再算。大结果集分批处理。

## JOIN 优化

小表驱动大表，注意连接列都有索引。多表 JOIN 要控制数量，必要时拆成多次查询在应用层合并。避免在 JOIN 条件里做函数运算。

## 子查询与 EXISTS

`IN` 子查询在大数据集上可能低效，`EXISTS` 通常更快，因为找到一条即可返回。相关子查询可能被优化器改写，但仍要实测。

## 事务与锁

长事务持有锁会阻塞其他请求，甚至引发死锁。事务内不要做网络调用或耗时计算。按固定顺序访问多张表可降低死锁概率。必要时降低隔离级别，但要评估一致性影响。

## 批量操作

逐条 INSERT 会产生大量往返。批量插入、`INSERT ... ON CONFLICT`、`COPY` 都能显著提速。批量更新用一条语句而不是循环。

## 缓存与预计算

热点统计可以定时预计算写入结果表，避免每次实时聚合。报表类查询用物化视图。缓存层放在数据库前面能减轻压力，但要处理失效。

## 常见坑

- 盲目加索引导致写入变慢
- 只看单次查询快，忽略并发下的锁竞争
- 用 offset 翻到很深的页
- 在事务里发 HTTP 请求
- 查询返回大量无用列
- 没有监控慢查询
