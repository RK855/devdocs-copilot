# 分页与过滤设计

## 分页的必要性

列表接口必须分页。一次性返回全部数据会拖慢响应、占用内存，前端也难以渲染。分页参数要有上限，避免客户端请求过大的页。

## offset 分页

`limit` + `offset` 是最直观的方案，适合中小数据量与需要跳页的场景。问题是深分页慢：数据库要扫描并丢弃前面所有行。数据量大时性能急剧下降。

响应通常包含 `total`、`page`、`page_size`、`has_next`。计算 total 需要额外 count 查询，大数据量下也有成本，可以改为“是否有下一页”。

## 游标分页

用上一页最后一条的排序键作为游标，查询条件为“大于该键”。不需要 offset，性能稳定，适合信息流与大数据量。缺点是不能随机跳页。

游标要编码排序键与唯一 id，避免重复值导致漏数据。游标内容应签名，防止客户端篡改。

## 排序稳定性

排序键不唯一时分页可能重复或遗漏。用“业务排序键 + 主键”做联合排序，保证全序。没有全序的分页在并发写入下结果不可预测。

## 过滤参数

过滤条件用查询参数，字段名与资源字段对应。复杂组合可以用 `filter[field]=value`，但要限制可过滤字段，避免任意字段查询导致索引失效。

多值过滤用逗号分隔或重复参数，需在文档中明确。空值与“未传”要区分，前者可能表示筛选空字段。

## 搜索与排序

关键词搜索与分页组合时，相关性排序与分页要一致，否则翻页结果不稳定。全文检索应使用搜索引擎而非数据库 LIKE。

## 缓存

相同分页参数可以缓存，但数据频繁变化时缓存收益低且容易不一致。第一页通常最热，可以单独缓存。

## 常见坑

- 不限制 page_size 上限
- 深 offset 分页
- 排序键不唯一导致翻页重复
- total 查询开销大
- 游标未签名可被篡改
