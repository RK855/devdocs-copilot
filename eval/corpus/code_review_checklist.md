# 代码审查清单

## 正确性

- 边界条件是否处理：空值、零、负数、超长输入
- 异常路径是否有兜底，失败时行为是否明确
- 并发场景是否存在竞争条件
- 状态机是否存在非法流转

## 可读性

- 命名是否表达意图，避免缩写与无意义变量名
- 函数是否只做一件事，长度是否可控
- 复杂逻辑是否有注释说明“为什么”
- 是否引入不必要的抽象

## 可测性

- 依赖是否可注入，能否用替身测试
- 是否耦合了全局状态、时间、随机数
- 新增逻辑是否配套测试，边界是否覆盖
- 测试是否断言行为而不是实现细节

## 安全性

- 用户输入是否校验与转义
- 是否拼接 SQL、命令、路径
- 权限是否在服务端校验
- 密钥是否硬编码或写入日志

## 性能

- 是否存在 N+1 查询
- 是否在循环里做网络调用
- 大对象是否全量加载
- 是否有不必要的重复计算

## 兼容性

- 接口字段变更是否向后兼容
- 数据库迁移是否可回滚
- 配置新增是否有默认值
- 依赖升级是否评估破坏性变更

## 错误处理

- 是否吞掉异常
- 日志是否包含足够上下文
- 错误信息是否对用户友好且不泄露内部细节
- 状态码是否语义正确

## 审查沟通

评论要具体、可操作，指出问题与建议，而不是只说“不好”。区分必须修改与可选建议。作者要回应每条意见，形成闭环。

## 常见坑

- 审查只挑格式问题
- 一次审查过多文件导致敷衍
- 只给否定不给方案
- 把个人偏好当规范
- 合并后不再跟进遗留问题
