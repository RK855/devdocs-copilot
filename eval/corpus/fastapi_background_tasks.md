# FastAPI 后台任务

## BackgroundTasks

`BackgroundTasks` 让响应返回后继续执行轻量任务，例如发送邮件、写审计日志。它在同一个进程内执行，不保证持久化，进程重启会丢任务。

```python
@app.post("/upload")
async def upload(file: UploadFile, tasks: BackgroundTasks):
    tasks.add_task(process, file.filename)
    return {"ok": True}
```

同步函数会被放进线程池，异步函数直接在事件循环执行。不要在后台任务里做超长阻塞操作，会拖住线程池或事件循环。

## 适用边界

适合“可丢失、短耗时、不需要重试”的任务。需要可靠执行的场景（订单、支付、批量导入）应使用消息队列与独立 worker，保证持久化、重试与可观测。

## 任务失败

后台任务的异常不会返回给客户端，只会出现在日志。必须自己记录失败原因，否则问题静默消失。任务应设计成幂等，重复执行不会产生副作用。

## 与流式响应的关系

流式接口返回后连接仍保持，后台任务与生成器共享事件循环。不要在流结束后才启动依赖请求上下文的任务，因为上下文可能已销毁。

## 依赖注入与后台任务

后台任务不会自动获得请求级依赖，例如数据库会话。会话在响应后可能已关闭，任务里再用会报错。正确做法是在任务内自行创建会话，或在任务开始前把所需数据取出并以普通参数传入。

## 超时与并发

后台任务没有内置超时，长任务会一直占用资源。可以包一层 `asyncio.wait_for` 或在任务内部检查耗时。并发量大时要限制同时运行的任务数，避免把进程拖垮。

## 分离 worker

当任务变重，应迁移到独立进程：API 只负责入队，worker 消费。这样 API 的延迟不受任务影响，worker 可以独立扩缩容。队列要能持久化，消费要能重试与死信处理。

## 常见坑

- 把重要任务放后台任务，重启即丢
- 任务里用已关闭的数据库会话
- 异常无人处理
- 长任务阻塞事件循环
- 没有去重，重复提交产生重复副作用
