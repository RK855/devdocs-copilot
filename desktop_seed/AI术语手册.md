## 一、基础模型类

### 1. LLM（Large Language Model，大语言模型）
**大白话**：就是你平时用的 ChatGPT、DeepSeek、通义千问这些"能聊天的 AI"。它读过海量文本，能理解你说的话，也能生成回答。

**你需要知道的**：
- 我们不训练 LLM（那是大厂的事，需要几千张 GPU）
- 我们是**调用 LLM 的 API**，给它发请求，它给我们回结果
- 就像调用一个"超级聪明的黑盒函数"：输入一段文字，输出一段文字

**常见的 LLM**：
- 国外：GPT-4o、Claude
- 国内：DeepSeek、通义千问（Qwen）、智谱（GLM）、Agnes（agnes-2.5-flash，本项目聊天模型 ⭐）

---

### 2. Embedding（嵌入 / 向量表示）
**大白话**：把一段文字变成一串数字（向量），意思相近的文字，它们的数字也会很"接近"。

**举个例子**：
- "苹果手机" 和 "iPhone" 意思接近 → 它们的向量距离很近
- "苹果手机" 和 "苹果水果" 意思不同 → 它们的向量距离较远

**为什么需要它**：
- 计算机不会"理解"文字，但它会算数字
- 有了向量，我们就能用数学方法来"找相似的文字"
- 这是 RAG 检索的基础

**常见 Embedding 模型**：
- OpenAI text-embedding-3
- 通义 embedding
- BGE 系列（中文效果好）；本项目使用硅基流动平台的 **BAAI/bge-m3，输出 1024 维向量** ⭐

---

### 3. Token（令牌 / 词元）
**大白话**：LLM 处理文字的基本单位。不是一个字一个字地处理，而是把文字切成一个个 token（大概 0.7 个汉字 = 1 个 token）。

**为什么重要**：
- LLM 有上下文长度限制（比如 128K token），超出的内容它"看不到"
- API 收费是按 token 算的，输入输出都要钱
- 做 RAG 的时候要控制 chunk 的 token 数量

---

## 二、RAG 与检索相关

### 4. RAG（Retrieval-Augmented Generation，检索增强生成）
**大白话**：让大模型在回答问题之前，先去"查资料"，然后再根据查到的资料回答。这样它就不会胡说八道（幻觉）了。

**为什么需要 RAG**：
- LLM 的知识是截止到某个日期的，最新的知识它不知道
- LLM 不知道你公司的内部文档、你的个人笔记
- 直接问 LLM，它可能会"一本正经地胡说八道"（幻觉）

**RAG 的两步走**：
1. **检索（Retrieval）**：根据你的问题，去知识库（向量库）里找最相关的几段文档
2. **生成（Generation）**：把找到的文档 + 你的问题一起发给 LLM，让它根据文档来回答

**就像考试开卷**：先翻书找答案，再根据书上的内容写回答。

---

### 5. 幻觉（Hallucination）
**大白话**：LLM 一本正经地胡说八道，说一些看起来很对但实际上是错的内容。

**为什么 RAG 能减少幻觉**：因为 LLM 是根据检索到的文档来回答的，不是凭空瞎编的。

---

### 6. 向量数据库（Vector Database）
**大白话**：专门用来存向量（Embedding）的数据库，能快速找出"和这个向量最相似的前 N 个向量"。

**类比一下**：
- 普通数据库：存表格，按关键字查询（`WHERE name = '张三'`）
- 向量数据库：存向量，按相似度查询（"找最像这个向量的前 5 个"）

**常见的向量数据库**：
- **Chroma**：轻量级，本地文件存储，适合原型 ⭐（**我们项目用这个**）
- pgvector：PostgreSQL 的插件，用 SQL 就能查，适合中小规模
- Milvus / Qdrant：专业级，适合大规模生产环境

---

### 7. 余弦相似度（Cosine Similarity）⭐
**大白话**：衡量两个向量"方向有多一致"的分数，用来判断两段文字语义有多接近。

把两个向量想象成从同一点射出的两支箭：

| 两支箭 | 夹角 | 余弦值 |
|---|---|---|
| 方向相同 | 0° | 1（最相关） |
| 方向垂直 | 90° | 0（无关） |
| 方向相反 | 180° | -1（相反） |

所以相似度范围是 **-1 到 1，越接近 1 越相关**。Chroma 返回的是"距离（distance）= 1 − 相似度"，代码里要自己换算回来。

---

### 8. 最近邻搜索与 HNSW ⭐
**大白话**：向量数据库的核心任务——"给我和这个坐标距离最近的 N 条记录"，叫最近邻搜索。

数据量大时，拿目标向量和库里每条记录都算一遍距离会慢死。所以实际用**近似最近邻（ANN）算法**：牺牲一点点精度换巨大的速度提升。

**HNSW** 是最经典的 ANN 算法之一（Chroma 默认使用），思路是"建多层小抄图，先粗看再细看"快速跳到目标附近。会念名字、知道它是干什么的即可。

---

### 9. 语义检索 vs 关键词检索 ⭐
- **关键词检索**：必须字面有相同的词才能匹配。搜"怎么启动"匹配不到写着"用 uvicorn 运行"的文档
- **语义检索**：用 Embedding 比较意思是否相近，不需要字面相同。基于向量数据库实现

本项目 Day 3 先用语义检索；Day 6 起把两者混合，互补短板。

---

### 10. Chunk（文本块 / 切片）
**大白话**：把一篇长文档切成一小块一小块的，每一小块叫一个 chunk。

**为什么要切**：
- 整篇文档太大了，不能全塞给 LLM（token 限制 + 费用高）
- 检索的时候返回整段文档太冗余，只要相关的那一小段就行
- chunk 太小会丢失上下文，太大又会引入噪声，所以 chunk_size 是个重要参数

**常见 chunk 大小**：300、500、800、1000 token

**项目参数 ⭐**：chunk_size=500 字符、chunk_overlap=50（相邻块重叠 50 字符，防止关键信息正好被切断）；用 LangChain 的 `RecursiveCharacterTextSplitter` 按"段落→换行→句号→硬切"的优先级找自然边界。

---

### 11. Ingest（摄入 / 索引构建）
**大白话**：把文档喂给系统的过程：读文档 → 切成 chunk → 生成 Embedding → 存入向量数据库。

**就像**：开卷考试前，你先把课本内容整理成小卡片，按知识点分类放好，考试时才能快速翻到。

项目中 md/txt 直接读取（UTF-8 失败用 GBK 兜底），pdf 用 `pypdf` 库逐页提取文本 ⭐。

---

### 12. EmbeddingFunction（嵌入函数，简称 EF）⭐
**大白话**：向量库和嵌入模型之间的"插座标准"。Chroma 不管你用哪家模型，只要求你提供一个函数：输入一批文本、输出一批向量。

好处：换嵌入模型时只改这一个函数，其他代码一行不动——这就是"解耦"。本项目实现为 `SiliconFlowEmbeddingFunction`，入库时 Chroma 自动调用它把文本变成向量。

---

### 13. Rerank（重排序，F7 已落地）
**大白话**：混合检索先粗选出 Top-10 个结果，然后用一个更精准的模型重新排序，选出最相关的 Top-5。

**为什么需要 Rerank**：
- 向量检索快但不够准（用的是 Embedding 的相似度，问题和文档编码时互不可见）
- Rerank 模型更准但慢（cross-encoder 把问题和每个候选拼一起逐对打分，见第 62 条）
- 所以先粗筛再精排，兼顾速度和准确率，这套结构叫两阶段检索（第 63 条）

**本项目实现**：硅基流动 `BAAI/bge-reranker-v2-m3`，`app/services/rerank_service.py`；返回的 relevance_score（0~1）直接成为来源卡分数；打分故障 fail-open 退回粗排顺序（第 65 条）；真实打分 top1 < 0.02 触发二次证据门拒答。

**常见 Rerank 模型**：bge-reranker 系列（本项目用 v2-m3，硅基流动免费、RPM 2000）、Cohere Rerank

---

### 14. BM25
**大白话**：传统的关键词检索算法（就是搜索引擎用的那种），根据关键词的匹配程度来打分。

**和向量检索的区别**：
- BM25：看关键词有没有匹配，匹配得多不多 → 擅长"精确匹配"
- 向量检索：看语义相不相似 → 擅长"语义匹配"

**为什么要混合用**：
- 比如用户问"FastAPI 的 `@app.get` 装饰器怎么用"
- BM25 能精准匹配到包含 `@app.get` 的文档
- 向量检索可能会找到"装饰器"相关但不是 FastAPI 的内容
- 两者结合（混合检索）效果更好

---

### 15. RRF（Reciprocal Rank Fusion，倒数排名融合）
**大白话**：把多个检索结果（比如 BM25 的结果 + 向量检索的结果）合并成一个排名的算法。

**原理很简单**：
- 每个结果的分数 = 1/(排名 + k)，k 是个常数（通常 60）
- 把不同检索方式给同一个结果的分数加起来
- 按总分重新排序

**不用深究原理**，知道它是"把多个检索结果融合在一起"的方法就行。

---

## 三、Agent 相关

### 16. Agent（智能体）
**大白话**：能自己思考、自己决定下一步做什么的 AI。普通的 RAG 是"检索 → 回答"的固定流程，Agent 是"思考 → 决定用什么工具 → 执行 → 再思考 → 再决定..."的循环。

**举个例子**：
- 用户问："FastAPI 怎么处理文件上传？顺便给我一个完整的代码示例。"
- 普通 RAG：直接检索文档，然后回答
- Agent：先想"这个问题需要查文档" → 调用检索工具 → 拿到结果 → 再想"用户要代码示例，我需要根据文档生成代码" → 生成代码 → 检查对不对 → 最后回答

**Agent 的核心要素**：
- **思考（Reasoning）**：LLM 自己想下一步该干嘛
- **工具（Tools）**：Agent 能用的工具（检索、计算器、搜索引擎等）
- **记忆（Memory）**：记住之前的对话和做过的事
- **观察（Observation）**：工具执行后的结果

> 📌 本项目 Day 9 已落地第一个 Agent（ReAct + `search_docs`，端点 `/api/agent/query`），详见词条 66/67 与《知识点手册》Day 9。

---

### 17. Function Calling（函数调用 / 工具调用）
**大白话**：LLM 不只是能说话，还能"调用函数"。你告诉它有哪些函数可以用、每个函数的参数是什么，它会根据用户的问题决定要不要调用函数、传什么参数。

**举个例子**：
- 你告诉 LLM：有个函数叫 `search_docs(query)`，可以搜索文档库
- 用户问："FastAPI 怎么启动？"
- LLM 决定调用 `search_docs(query="FastAPI 启动方式")`
- 你的代码拿到这个调用，去执行检索，把结果返回给 LLM
- LLM 再根据检索结果生成最终回答

**为什么重要**：这是 Agent 能"做事"的基础——通过 Function Calling，LLM 可以使用各种工具。

---

### 18. LangChain
**大白话**：一个 Python 框架，把做 AI 应用常用的东西都封装好了，让你不用从零写。

**LangChain 提供什么**：
- 对接各种 LLM（OpenAI、DeepSeek、通义...）
- 对接各种向量数据库（Chroma、pgvector、Milvus...）
- 各种文档加载器（PDF、Word、Markdown...）
- 各种链（Chain）和 Agent 模板
- Rerank、混合检索等高级功能

**类比**：就像后端开发用 Spring Boot，前端用 React，做 AI 应用大家常用 LangChain。

---

### 19. LangGraph
**大白话**：LangChain 团队出的另一个框架，专门用来构建 Agent 和有状态的多步工作流。

**和 LangChain 的关系**：
- LangChain：提供各种组件（积木）
- LangGraph：把组件组装成复杂的、有状态的工作流（搭积木的图纸）

**为什么需要它**：做 Agent 的时候，需要管理状态、控制循环、处理分支，LangGraph 就是干这个的。

---

## 四、Python 与 Web 工程化

### 20. FastAPI
**大白话**：Python 里最火的 Web 框架之一，用来写 API 接口。性能好、代码简洁、自动生成 API 文档。

**类比 Java**：相当于 Java 里的 Spring Boot，但更轻量、上手更快。

---

### 21. uvicorn 与 ASGI ⭐
- **ASGI**：现代 Python 处理 Web 请求的规范，支持异步；旧规范叫 WSGI（Flask 那一代，仅同步）
- **uvicorn**：按 ASGI 规范干活的服务器——真正监听端口、收请求、转给 FastAPI、发响应的程序

启动命令 `uvicorn main:app` 里，`main:app` 指 main.py 文件中名为 app 的实例。

---

### 22. Pydantic ⭐
**大白话**：Python 最流行的数据校验库，FastAPI 的内置搭档。你只要用类型注解声明字段（`doc_id: str`、`chunk_count: int`），它自动负责：

1. 校验数据合不合法（不合法自动返回 422 错误）
2. 各种格式自动转换（JSON ↔ Python 对象）
3. 序列化输出

本项目的 `app/schemas.py` 全是 Pydantic 模型，就是前后端之间的数据契约。

---

### 23. HTTP 方法与状态码 ⭐
**常用方法**（表达"要干什么"）：GET 取数据、POST 提交数据、DELETE 删除数据、PUT 更新数据。

**常见状态码**（表达"结果如何"）：

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 客户端请求有问题（如文件格式不支持） |
| 404 | 资源不存在 |
| 422 | 请求格式对但内容校验没通过 |
| 500 | 服务器内部错误 |

写 API 的纪律：**让状态码说真话**——用户的错别返回 500。

---

### 24. Python 装饰器（Decorator）⭐
**大白话**：以 `@xxx` 开头、写在函数上面的语法，作用是"给这个函数挂上额外的能力或登记"。Java 注解的亲戚。

比如 `@router.post("/upload")` 就是把下面的函数登记成"/upload 接口的处理人"；函数本身的代码不用变。

---

### 25. 异步编程：事件循环、协程、async/await ⭐
**大白话**：让一个线程在"等待网络/硬盘"的间隙穿插处理很多任务的编程方式。

- **事件循环（Event Loop）**：那个负责穿插调度的"调度员"，类比不停转场服务多桌的服务员
- **协程（Coroutine）**：可以中途暂停、之后再接着干的函数，用 `async def` 定义
- **await**：协程里的"暂停点"——等 I/O 的时候把线程让给别的任务，而不是干等

`await` 只能写在 `async def` 里面。

---

### 26. 阻塞调用与 asyncio.to_thread ⭐
**阻塞**：一个调用在原地死等结果、不把控制权交还，整个事件循环被它一个人钉住，所有用户的请求一起卡死。这是异步服务最容易犯的致命错误。

**解法**：`asyncio.to_thread(函数, 参数)`——把阻塞活儿扔到旁边的线程池里干，事件循环继续服务别人。

判断口诀：**I/O 密集型**（大部分时间在等，如 Web 服务）用异步能大幅提并发；**CPU 密集型**（大量计算）异步帮不上忙，要靠多进程。

---

### 27. SSE（Server-Sent Events，服务器推送事件）⭐
**大白话**：一种让服务器能主动给前端发消息的技术，用来做"流式输出"（就是 ChatGPT 那种一个字一个字蹦出来的效果）。

**为什么用 SSE 不用 WebSocket**：
- SSE 更简单，单向通信（服务器 → 客户端）
- WebSocket 是双向的，但更复杂
- 流式输出只需要服务器推给前端，SSE 刚好够用

> F9 Day 12 已落地：`POST /api/chat/stream` 返回 `text/event-stream`，帧格式 `event: 名字\ndata: JSON\n\n`，事件序 meta→sources→delta×N→done（故障发 error 不发 done）。注意浏览器原生 EventSource 只支持 GET，本项目问题在请求体里，所以前端用 fetch + ReadableStream 手写解析——详见《知识点手册》Day 12 与第 71 条「流式输出」。
>
> Day 16 追加：SSE 不只用来推"答案文本"，也能推**执行进度**——`POST /api/agent/stream` 用同款帧格式推 phase→tool_start→tool_end→…→done（终态整包，非逐字答案），详见第 83 条。

---

### 28. lifespan（生命周期）⭐
**大白话**：规定应用"开业时先干嘛、打烊时收什么"的机制。本项目用它在启动时确保 uploads、data 目录存在；以后重建索引、关闭连接也挂这里。

---

### 29. 分层架构与依赖注入 ⭐
**分层**：把代码按职责分层，本项目是 `routes 接口层 → services 业务层 → db 数据层`。依赖只能从上往下，不准反向。

**依赖注入（DI）/控制反转**：一个组件需要的外部能力（比如向量库）由外部"递进来"，而不是自己写死。组件只依赖"有哪些方法"这个约定，不依赖具体实现——所以测试时可以注入一个假的仓库（FakeStore），脱离网络和数据库跑业务测试。思想和 Java 的 Spring 完全一样。

---

### 30. venv 虚拟环境 ⭐
**大白话**：给每个项目单独配一个"依赖储物间"。A 项目要 fastapi 0.14、B 项目要旧版，互不干扰。命令：`python -m venv venv`。

---

### 31. 环境变量与 .env ⭐
**大白话**：把"因环境而异或敏感"的东西（API Key、端口、路径）从代码里拿出来，放进 `.env` 文件。程序运行时读取它。

安全纪律：`.env` 必须被 `.gitignore` 忽略、永不进 Git；对外只提供写满占位符的 `.env.example`。

---

### 32. UUID
**大白话**：一种全球唯一的随机 ID 生成规则（一串十六进制字符），不用发号器也不会撞 ID。

本项目用 `uuid4().hex` 给每个文档生成 doc_id；上传的源文件还会加 doc_id 前缀，防止两个用户传同名文件互相覆盖。

---

### 33. 字符编码：UTF-8 / GBK ⭐
**大白话**：文字在电脑里其实也是数字，"编码"就是文字↔数字的对照规则。乱码就是用错了对照表。

- UTF-8：现代通用编码，优先使用
- GBK：中文 Windows 的老编码，网上下的老 txt 可能是它

本项目解析文本的策略：先按 UTF-8 解，失败再兜底按 GBK 解。

---

### 34. Docker
**大白话**：把你的应用和它需要的所有依赖打包成一个"集装箱"，在哪都能跑，不会出现"我电脑上能跑啊"的问题。

**为什么 AI 项目特别需要 Docker**：
- Python 依赖特别多，版本容易冲突
- 向量数据库等组件安装配置麻烦
- Docker Compose 一条命令就能把多个组件都启动起来

---

### 35. Docker Compose
**大白话**：用来管理多个 Docker 容器的工具。比如你的项目需要一个 Python 应用容器 + 一个数据库容器，Docker Compose 可以一键启动、停止、管理它们。

---

## 五、测试相关

### 36. TDD（Test-Driven Development，测试驱动开发）⭐
**大白话**：一种写代码的纪律——先写测试（描述"我要的行为"）并亲眼看它失败（红灯），再写代码让它通过（绿灯），最后在测试保护下整理代码（重构）。

"先看失败"为什么是铁律：不然你无法证明这个测试真的在检测东西，可能写了个无效测试。

---

### 37. pytest 与常用 fixture 机制 ⭐
**大白话**：Python 最主流的测试框架。常用机制：

| 机制 | 用途 |
|---|---|
| fixture | 测试前的准备工作，函数参数自动注入 |
| tmp_path | 给每个测试一个独立临时目录，用完即焚 |
| monkeypatch | 临时替换配置/属性，测完自动还原 |
| parametrize | 一个测试喂多组数据 |
| TestClient | 不开端口，直接把 HTTP 请求打进 FastAPI 应用做接口测试 |

---

### 38. 单元测试 vs 集成测试 ⭐
- **单元测试**：只测一个小组件，外部依赖全用假对象（如 FakeStore），快、定位准
- **集成测试**：真实组件拼装运行（真调 API、真写数据库、真走 HTTP），慢一点但证明"拼起来真能转"

重要纪律：测试必须引用线上同一份代码，禁止复制一份"专供测试"的实现。

---

## 六、检索评测相关

### 39. Recall@K（召回率）
**大白话**：在前 K 个检索结果里，命中了多少个"应该被找到的文档"。

**举个例子**：
- 某个问题，正确答案在文档 A 和文档 B 里
- 检索返回了 Top-5 结果，其中包含了文档 A，但没包含文档 B
- 那 Recall@5 = 1/2 = 50%

**越高越好**，说明检索越全面。

---

### 40. MRR（Mean Reciprocal Rank，平均倒数排名）
**大白话**：衡量第一个正确结果排第几的指标。排得越靠前，分数越高。

**举个例子**：
- 问题 1：第一个正确结果排第 1 位 → 1/1 = 1.0
- 问题 2：第一个正确结果排第 3 位 → 1/3 ≈ 0.33
- MRR = (1.0 + 0.33) / 2 ≈ 0.67

**越高越好**，说明检索结果排序越好。

---

## 七、Prompt、调用保障与测试替身

### 41. Prompt 与 Prompt 工程（提示词工程）⭐
**大白话**：Prompt 就是你发给 AI 的完整指令文本；Prompt 工程是研究"怎么把话说清楚，AI 才照你想要的做"。

例子对比：
- "写个东西" → 模型自由发挥，大概率不是你要的
- "你是 Python 专家。只依据我给的资料回答，用 Markdown，代码块标语言，资料没有就明说。资料如下：……" → 行为被框死

RAG 里的 Prompt 通常 = 角色设定 + 回答规则 + 参考资料 + 用户问题。

---

### 42. 消息角色（role：system / user / assistant）⭐
**大白话**：对话接口的每条消息都要标注"这句话是谁说的"：

| role | 身份 | 作用 |
|---|---|---|
| system | 系统 | 定规矩、定人设（行为宪法，只发一次） |
| user | 用户 | 提需求、提问题 |
| assistant | 助手 | 模型自己的历史回答（多轮对话时传回） |

分开角色是为了让模型区分"必须遵守的规则"和"本次要处理的请求"。

---

### 43. Temperature（温度）⭐
**大白话**：控制模型回答"有多放飞"的旋钮，一般在 0~2 之间。

- 调到接近 0：回答保守、稳定、可复现 → **查资料/写代码用低温（本项目 0.3）**
- 调高（1 以上）：用词随机、有创意 → 写诗、写广告文案才用

---

### 44. 超时与重试（Timeout / Retry）⭐
**大白话**：调用远程接口的两道保险：

- **超时**：约定"等多久还不回应就算失败"，避免无限干等
- **重试**：失败后再发一次。但只对**临时故障**（超时、网络抖动、服务器 5xx）有用；Key 错了（401）重试一百次也没用，应立即报错

"重试几次、等多久再试"是后端面试常聊的可靠性基本功。

---

### 45. Stub / Mock（桩 / 模拟对象）⭐
**大白话**：测试时给真实依赖找的"替身演员"：

- **Stub（桩）**：你问什么它都按剧本回答固定内容（如假的 LLM 永远返回"这是测试答案"）
- **Mock（模拟）**：除了给答案，还负责检查"我被调用了几次、参数对不对"

好处：测业务逻辑时不用真调 API、真连数据库——快、稳定、不花钱。本项目用"依赖注入"把替身递进去。

---

### 46. 拒答门槛（相关性阈值，Relevance Threshold）⭐
**大白话**：检索回来的片段即使有结果，也可能全都不太相关。于是画一条分数线：最高分低于它，就判定"知识库里没有"，直接回复拒答、不调用大模型——省时间、省成本。

本项目阈值为 0.45，是用真实观测校准的：相关问题得分 0.76、无关问题 0.35，取两者之间。

---

## 八、前端与浏览器相关（F4）

### 47. DOM（Document Object Model，文档对象模型）
**大白话**：浏览器把 HTML 拆成一棵"家谱树"，每个标签是一个节点，JS 就靠修改这棵树来改变页面（加一行列表、改一段文字）。你改的不是原始 HTML 文件，而是浏览器内存里的树，刷新就没了。

### 48. fetch API
**大白话**：浏览器里的"requests"。JS 用它给后端发 HTTP 请求拿数据。坑点：服务器返回 400/500 时它**不报错**，只在断网时才报错，所以要自己看 `response.ok`。

### 49. FormData 与 multipart/form-data
**大白话**：普通 JSON 只能装文字，上传文件要用 FormData 这个"文件袋"把文件装进去，浏览器自动在外面套 multipart 格式的信封——后端 FastAPI 用 `UploadFile` 拆这个信封。

### 50. Promise / async-await（JavaScript）
**大白话**：JS 版的"将来给你结果的欠条"。发请求是异步的，不能干等，于是用 `.then()` 或 `async/await` 写明"数据回来后接着干什么"，写法和 Python 的 await 几乎一样。

### 51. CSS 变量（自定义属性）与主题切换
**大白话**：把颜色、字号起成名字（变量）集中管理，换深色/浅色时只改这一组名字的取值，全站自动跟着变，不用挨个组件改样式。

### 52. localStorage
**大白话**：浏览器给网页的一个小本本，键值都是字符串，关浏览器也不丢。本项目用它记住你选的深色还是浅色主题。

### 53. CDN（Content Delivery Network，内容分发网络）
**大白话**：第三方库（Marked、Highlight）放在离你近的服务器上，`<script src>` 直接引，不用下载安装。代价是依赖网络，所以代码里写了"加载失败就用纯文本兜底"。

### 54. 响应式设计与媒体查询（Media Query）
**大白话**：同一套页面自动适配宽屏和手机。`@media (max-width: 860px)` 就是"屏幕窄于 860 像素时启用这套样式"，本项目窄屏时左栏自动变成滑出抽屉。

### 55. XSS（Cross-Site Scripting，跨站脚本攻击）
**大白话**：坏人把恶意脚本当"内容"塞进页面，浏览器当代码执行。防线：给用户看的文本用 `textContent`（自动转义），只有自家后端返回的可信内容才用 `innerHTML`。

### 56. E2E 测试（End-to-End，端到端）与 Playwright
**大白话**：不看代码内部，直接模拟真人操作浏览器——打开网页、传文件、点按钮、看结果对不对。Playwright 就是干这个的工具，本项目 F4 用它做了 7 项验收，和后端 pytest 的单元测试互补。

---

## 九、BM25 与中文检索（F5）

### 57. 倒排索引（Inverted Index）
**大白话**：普通索引是"文档里有哪些词"，倒排索引反过来记"每个词出现在哪些文档里"。搜词时直接查表拿候选，不用翻遍所有文档——搜索引擎和 BM25 的底层都是它。

### 58. 分词（Tokenization）与 jieba
**大白话**：把连续文本切成一个个可检索的词。英文有空格天然分好，中文"红烧肉怎么做"得靠工具切，本项目用 jieba（`jieba.lcut`）。关键纪律：**建索引和查询必须用同一个切词函数**，否则两边对不上。另外代码标识符（`query_similar`、`@app.get`）要单独保护，不能被当普通中文拆碎。

### 59. TF-IDF 与 IDF（逆文档频率）
**大白话**：TF 是词在一篇文档里出现的频率（出现越多越相关，但有饱和上限）；IDF 是词的稀有度——篇篇都有的"的/是"权重低，少数文档才有的"uvicorn"权重高。BM25 就是 TF-IDF 思想的改良版（加了文档长度归一化）。小语料里 IDF 可能为负（词出现在过半数文档中），这是公式特性不是 bug。

---

## 十、混合检索（F6）

### 60. 混合检索（Hybrid Search）
**大白话**：同时用"懂意思"的向量检索和"认死理"的关键词检索，再把两份排名合成一份。语义类问题（怎么跑起来）靠向量救，精确类问题（`@app.post`、报错串）靠关键词救，两边都认可的结果排最前。本项目用 RRF 做融合（见第 15 条）。

### 61. 停用词（Stop Words）
**大白话**："的、了、是、怎么、the、is"这种几乎每句话都有的词，对区分文档毫无贡献。检索前要在分词阶段把它们扔掉——否则任何中文问句都因一个"的"字跟所有文档"命中"，关键词检索的空结果信号直接报废。

---

## 十一、Rerank 精排与评测落地（F7）

### 62. bi-encoder 与 cross-encoder（双塔 / 交叉编码器）
**大白话**：两类"判断问题和文档相不相关"的模型。bi-encoder（如 bge-m3）让问题、文档**各自**编码成一个向量，再比余弦——各算各的，文档向量能离线预存，便宜快；cross-encoder（如 bge-reranker）把问题和文档**拼在一起**过模型，词与词互相看见后才吐一个相关性分——更准，但每对都要现算，只能精排小候选集。

### 63. 两阶段检索（粗排 → 精排，Two-Stage Retrieval）
**大白话**：先让便宜模型（向量 + BM25/RRF）从全库快速捞回十来条"可能相关"的（重召回），再让贵的 cross-encoder 对这十来条逐条精算取前五（重排序）。本项目线上链路：两路各 20 → RRF 取 10 → rerank 取 5。

### 64. Precision@K（精确率）与金标（Ground Truth）
**大白话**：返回的前 K 条里有多少是"对的"——Recall@K 管"该找的找没找全"，Precision@K 管"给出去的货纯不纯"，MRR 管"最对的排第几"。**金标**就是人工标注的"这题正确答案在哪个文件的哪个 chunk"，评测脚本拿它自动判分。注意：标注粒度会影响指标——每题只标一个金块时，Precision@5 结构上最高也就 1/5。

### 65. fail-open（故障放行）与 scored 标记
**大白话**：增强型服务（这里是 rerank）挂掉时，系统选择"降级继续服务"而不是"整体报错"。本项目 rerank 重试耗尽后退回粗排原顺序照样回答；返回结构带 `scored` 标记区分"真精排分/降级粗排分"，二次证据门只在真精排分时生效——供应商故障绝不演变成大规模误拒。与之相对的是 fail-closed（宁可不答也不降级），安全敏感场景才用。

---

## 十二、Agent ReAct 落地（F8 Day 9-10）

### 66. ReAct（Reasoning + Acting，推理行动循环）⭐
**大白话**：Agent 的主流干活套路——**想（Reason）→ 做（Act）→ 看观察（Observe）→ 再想**，一圈圈转，直到能给出最终答案。名字是论文自造的合成词（Reason+Act），不用当成高深理论，它就是个带工具的 while 循环。

**本项目里的样子**（`agent_service.run_agent`）：
1. 把工具清单（OpenAI tools schema）连同问题发给 LLM
2. LLM 要么直接给最终答案（循环结束），要么回一个/多个 tool_calls（"我要搜这个"）
3. 代码执行 `search_docs`，把结果以 tool 消息回喂
4. LLM 看完观察结果：命中就答，没命中就**换个关键词再来一轮**
5. 最多转 `AGENT_MAX_STEPS=5` 轮，防止失控烧钱

**真实冒烟**：问"红烧肉怎么做好吃"，模型连查 4 轮（中文→英文→换词→末轮并行两个）全是 0 命中，最后统一拒答——没人教过它"红烧肉"在步骤几出现，是 ReAct 循环 + 工具观察让它自己学会了"再试一次"和"放弃"。

**护栏**（Agent 比 RAG 多出来的活儿）：最大步数、同参缓存（不许用相同参数重复搜）、参数错误回喂自纠、工具异常不炸循环、零证据统一拒答、跨步骤来源去重。

---

### 67. Tool Call（工具调用消息与配对协议）⭐
**大白话**：Function Calling 在对话消息层面的具体载体。模型说"我要调函数"时，返回的不是普通文字，而是结构化的 tool_call；你的代码执行完，必须按它给的"回执编号"把结果配对回喂，对话才合法。

**协议三要素**（OpenAI 兼容接口）：
- **assistant 消息带 tool_calls**：`[{id: "call_abc", type: "function", function: {name: "search_docs", arguments: '{"query":"..."}'}}]`——注意 arguments 是 **JSON 字符串**，模型拼错时解析会失败（本项目抛 `ToolArgumentsParseError`，代码以 user 消息提示它重发）
- **tool 消息配对**：每条 tool 消息必须带 `tool_call_id` 指回上面的 id；一轮多个调用就有多条 tool 消息，编号一一对应，错配/漏配 API 直接报错
- **并行调用**：模型可以在一轮里吐多个 tool_calls（冒烟实测第 1 步同时发了中文、英文两条检索），它们共享同一个 step 编号，代码并发/顺序执行后分别回执

**类比**：像医院叫号——assistant 喊号（call_abc 查血常规、call_def 查尿检），工具科室做完检查必须把报告写上对应叫号单交回，医生（模型）才能拿着齐套报告下诊断。

---

### 68. 接地 / Grounded Generation（接地生成）⭐
**大白话**：要求模型生成的内容必须**站在检索证据上**——先查到资料才允许开口，查不到就明说或拒答，不许凭参数记忆"裸写"。"接地（Grounding）"就是把悬空的生成接到事实上，是 RAG 抗幻觉思路在 Agent 工具上的延伸。

**本项目里的样子**（Day 10，`generate_code_example`）：
- 工具执行时先看 `ctx.hits_seen`：**没有任何检索命中就不生成代码**，只回一句"请先用 search_docs 检索"的引导（该结果带 `cacheable=False` 不进缓存——检索完成后同参再调必须真执行，否则 Agent 会被旧拒绝卡死，详见《知识点手册》Day 10）；
- 有命中时，代码基于跨步骤累积的接地证据（top 8 chunk）+ 专用系统提示词生成，真实冒烟中模型先并行两条 search_docs、再调本工具产出含 `@app.get("/health")` 的可运行示例；
- 精确的放宽边界：`explain_error` 是唯一允许零命中作答的内容型工具（`produces_answer` 标记放行通用排查建议），而模型零工具零证据硬答仍一律拒答——接地约束是**精确开洞**，不是整体拆除。

### 69. 执行轨迹 / Agent Steps 与可观测性（Observability）⭐
**大白话**：Agent 回答时把"我先干了什么、后干了什么"一步步列给你看——查了哪几个词、命中几条、有没有走缓存、调了哪个工具。没有这条轨迹，Agent 就是个黑箱：答案对了你不知道为什么对，拒答了你怀疑它根本没查。**可观测性（Observability）**就是让系统的内部过程从外面看得见、查得明，是 Agent 产品区别于"聊天框套壳"的标配。

**本项目里的样子**（Day 10 前端包，`/api/agent/query` 响应的 `steps` 字段）：
- 每步记录 `step`（第几轮，同一轮并行两个工具调用编号相同——并行事实一眼可见）、`tool`（工具名，前端映射成中文：检索文档/生成代码示例/分析报错）、`arguments`（入参，如查询词、任务、报错信息）、`result_count`（带回几条结果，内容型工具恒为 0）、`cached`（同参重放走缓存时显示「缓存命中」徽标）；
- 前端渲染为答案下方的**折叠轨迹卡**，摘要一行给全貌（「执行步骤 3 检索文档 → 检索文档 → 生成代码示例」），默认折叠不抢正文，展开才看参数；
- 拒答时轨迹照样展示：真实冒烟中库外问题（"Django 怎么配置 PostgreSQL"）两轮检索全 0 条结果后拒答，REJECT 标签与零结果轨迹同屏——检索过程本身就是"我确实查过、真没有"的证据；
- RAG 端点没有 steps 字段，前端靠"响应里有没有 steps"做增量分流，老契约零改动；
- Day 11 起每步再带 `status`（ok/empty/error）与 `error` 短因：绿色「N 条」=有产出、灰色「0 条」=查过没有、红色「失败」=没查成（详见第 70 条）。

### 70. 失败三态与降级 / Degraded（Partial Failure，部分失败）⭐
**大白话**：系统出状况时有三种完全不同的处境，不能用一句话糊弄：①**查过了，真没有**（empty，该说"没有"）；②**我自己坏了，没查成**（error，该说"稍后重试"）；③**坏了一半但还能答**（degraded，答照给但要声明"可能不完整"）。**部分失败（Partial Failure）**指分布式系统里多个依赖/步骤只挂了一部分——整体请求不必二选一地"全成功或全失败"，能降级交付就降级交付，但必须如实标注。

**本项目里的样子**（F8 Day 11）：
- 每步工具结果三态：`ok` / `empty`（检索管线正常但零命中，进缓存）/ `error`（异常、参数非法、接地拒绝，不进缓存）；
- 终局三判：零工具直拒或有任一 search 成功执行过 → `mode=reject`（统一拒答话术）；取证全程 error 或主 LLM 致命异常且零证据 → `mode=error`（固定话术"检索服务暂时异常，请稍后重试。"，**HTTP 仍 200**，steps 失败轨迹照常返回）；部分步骤失败但仍组织出答案 → `mode=agent` + `degraded=true`；
- 前端：error 显橙色错误横幅且不渲染来源卡，degraded 在答案顶部插"部分工具执行失败，以下回答可能不完整"提示条；
- 设计要点：error 态返回 200 是因为它是**符合契约的正常业务响应**（带可预期的固定文案与轨迹），不是服务器无法应答；5xx 留给真正的未捕获故障——而主 LLM/工具的异常已被全部兜底，理论上不再漏出 500。

**面试一句话**：区分"没有"和"坏了"是可观测性的底线；部分失败时降级作答 + 显式 degraded 标记，比"要么完美要么报错"更符合真实系统的可用性要求。

## 十三、流式输出 SSE 落地（F9 Day 12）

### 71. 流式输出（Streaming / Token-by-Token，流式生成）⭐
**大白话**：模型不再"憋 40 秒给一整篇"，而是每生成几个字就吐一块，前端一块一块接、一块一块显示——打字机效果。技术上对应 OpenAI SDK 的 `stream=True`：返回的不是完整响应，而是一个可以 `for ... in` 迭代的流，每块带增量内容 `delta.content`。

**本项目怎么落地**：后端把增量包成 SSE 的 `delta` 事件逐帧 yield；前端流式期间只用 `textContent` 追加纯文本（带闪烁光标），整段结束（done 或中断）后才一次性做 Markdown 渲染——边收边重渲染又卡又闪。**错误按"发生在第几个字"分类**：零字失败=llm_unavailable、已有字后失败=stream_interrupted（已收内容保留+重试），区别于检索阶段就挂掉的 retrieval_failed。

### 72. AbortController（中止控制器 / fetch 取消请求）⭐
**大白话**：浏览器给的一个"遥控器"，`const ctrl = new AbortController()`，把 `ctrl.signal` 传给 fetch；想取消时点 `ctrl.abort()`，进行中的请求和读流立刻抛出 AbortError。用来实现聊天框的「停止生成」按钮——纯客户端行为，不用和服务器约定新协议；服务器检测到 TCP 断连后负责关闭上游 LLM 流，不再白烧 token。

**配套细节**：发送键在流式期间变红、文案变「停止」且保持可点；RAG（Day 12）与 Agent（Day 16 起走 `/api/agent/stream`）两种模式都有停止按钮。停止后已收到的内容保留，下方给「重试」；重试复用原气泡重新流式，不新增用户消息。Agent 的停止还会让服务端 cancel 掉后台执行任务，后续轮次的模型调用不再发出（省 token）。

### 73. 同步→异步桥接（Sync-to-Async Bridge，线程 + 队列生产者消费者）⭐
**大白话**：FastAPI 的接口是 async 的，但我们用的 OpenAI SDK 和大量测试 Fake 都是同步的——两套节奏不能直接接。桥接做法：开一个后台 worker 线程专门在里面迭代同步流，用两个队列（命令队列、输出队列）和 async 侧传话：异步侧喊"下一块"，worker 线程取到就丢回输出队列；async 侧用 `run_in_executor` 阻塞等队列，不卡住事件循环。

**为什么值得讲**：①同步迭代器只能在一个线程里创建/迭代/关闭（"谁创建谁关闭"），不能多线程乱碰；②客户端断连时，ASGI 框架是在生成器 yield 的位置抛 `GeneratorExit`（不是 CancelledError，捕错类型就漏清理），所以关闭上游的动作必须放 `finally`，保证正常结束、报错、用户点停止三种路径都会关掉上游流。这是典型的"生产者-消费者 + 资源确定性释放"面试题。

### 74. 429 限流与指数退避（Rate Limit / Exponential Backoff）⭐
**大白话**：你调 API 太频繁或供应商当时拥塞，服务器回 **429 Too Many Requests**——"忙，等会儿再来"。正确做法不是立刻重发（大家都立刻重发会把服务器再冲垮一次，叫"惊群"），而是等一小会儿再试，且每多失败一次就把等待时间翻倍式拉长，这就是**指数退避**。本项目 429 最多重试 2 次，等待 1s → 3s。

**配套细节（按错误病因开不同药方）**：401/403（API Key 无效/缺失）重试再多次也不会好，**立即失败**并提示"模型服务认证失败，请检查配置"；超时/连接错误/5xx 是临时故障，重试 1 次。另注意区分两个概念：**构造期错误**（没配 Key，客户端都建不起来，归一为 LLMConfigError）不阻塞服务启动，只在真正对话时返回友好文案；业务失败统一回 HTTP 200 + `mode="error"`（错误是"成功送达的终态内容"，不是传输层故障）。面试可延伸：退避常配 **jitter（随机抖动）** 进一步打散同时重试的客户端。

## 十三补、文档摄入扩展（Day 13+）

### 75. OOXML 与 .docx / .doc 之辨（Word 文档解析）⭐
**大白话**：Word 有两代格式，别当成一回事。**`.docx`（2007 后）= OOXML**，本质是个 zip 压缩包，里面装 XML，Python 用 `python-docx`（底层 lxml）不装 Office 就能读出段落和表格；**`.doc`（2003 前）= OLE 老二进制格式**，Python 没有轻量解析方案，要靠 LibreOffice 转换或 Windows COM 调 Word，又重又挑平台。

**本项目里的样子**：校验白名单收 `.docx` 不收 `.doc`（提示用户另存为新格式）；解析器把段落与表格单元格拼成纯文本交切分器，docx 无页码概念（page 恒为 None）。调试暗号：垃圾字节喂给 python-docx 会抛 `zipfile.BadZipFile`——解压失败就等于"这不是合法 docx"。另：**扫描件 PDF 同理有坑**，pypdf 只能提文字层，图片扫描页提取不出字，要 OCR（本项目未做）。

### 76. 灌库 / Seeding 与幂等（Idempotency）⭐
**大白话**：**灌库（Seeding）**是系统上线/初始化时把一批现成文档批量喂进数据库的动作，区别于用户在界面上一个个上传。**幂等（Idempotency）**是同一个操作执行一次和执行 N 次结果相同——灌库脚本可能反复重跑（加了新文件再跑一次），绝不能把旧文档重复嵌入几遍。

**本项目里的样子**（`python -m app.scripts.seed <目录> [--recursive]`）：以**文件名**为幂等键，库中已有的同名文件跳过，只入库新文件；单文件失败只记录不中断整批，有失败时退出码 1。脚本直接复用网页上传的 `ingest_document()` 全链路（校验→解析→切分→落盘→Chroma→BM25），保证"灌进去的"和"传上去的"是同一种数据。BM25 是内存索引不用管——服务启动时自动从 Chroma（唯一持久事实源）重建。

### 77. 批量上传与前端任务队列（Client-side Queue）
**大白话**：一次选多个文件上传有两种做法——后端开多文件接口，或前端排队逐个调单文件接口。后者（本项目采用）零新契约：一个数组当队列，循环每次取一个文件发请求，某个失败不拖累其他文件，上传区实时显示"队列剩余 N"。通用模式叫**任务队列（Task Queue）**：生产端（选择/拖拽）只管入队，一个"泵（pump）"负责串行消费，运行中追加任务也能自然排空。注意前端的类型拦截只是体验优化，**服务端白名单才是最终闸门**——永远不能信任客户端校验。

### 78. 元数据标记（Metadata Tagging）与数据溯源（Data Provenance）
**大白话**：**元数据标记**是给每条数据盖个"身份小标签"（谁产生的、从哪来、什么时间），**数据溯源**就是日后凭标签回答"这条数据哪来的"。关键纪律有两条：① 标签要在**写入时**盖、跟着数据一起持久化（本项目灌库的 chunk 盖 `source=seed`、网页上传盖 `source=upload`，盖在 Chroma metadata 里），不能靠外挂文件或目录名事后推断，否则数据一搬家就失忆；② 标签只服务"列表/管理"这类溯源场景，**不污染检索**——预置语料和上传语料在问答时一视同仁。老数据没有标签时用一次性**回填（Backfill）**脚本补齐：只原地改 metadata，不重新调 embedding，且做成幂等（重跑第二次补 0 条）。

**本项目里的样子**：标签只在「全部/预置/我的上传」这类管理视图里被读取；问答检索时 seed/upload 一视同仁。老数据没标签时用回填脚本原地补 metadata（Chroma `update` 是覆盖语义，要带完整字典），幂等可重跑。

## 十三补续、文档级检索范围（Day 13++ 续）

### 79. 检索范围过滤（Scoped Retrieval / Doc-Level Filtering）⭐
**大白话**：默认问答是"翻遍整个图书馆"，**范围检索**是"只许翻我指定的这几本书"——检索时带一个文档 id 白名单，白名单外的书再相关也不许进答案。通用产品形态就是各类搜索框旁的"在以下范围内搜索"。

**本项目里的样子**：请求体多一个可选 `doc_ids: list[str] | None`（省略=全库；上限 100 个、单 id ≤64 字符，越界 422），三个问答端点共用，RAG 和 Agent 都生效；服务端**不存会话状态**——"预置语料/我的上传"是前端视图概念，发请求前由前端翻译成 id 列表，范围随每个请求走（Agent 多轮则挂在 AgentContext 上，每轮工具检索都带同一组 id）。空列表与不传归一为全库；范围内查不到就是零证据，走正常拒答，不特判。

### 80. 过滤先于截断（Filter before Top-K）与谓词下推（Predicate Pushdown）⭐
**大白话**：检索是"从一堆候选里按分数取前 K 个"。范围过滤必须在**取候选的那一刻**就生效，不能等前 K 名出炉再把范围外的剔掉——否则范围外的高分选手会先占光 K 个名额，剔完之后范围内只剩残羹甚至空盘，召回率被悄悄打穿。这和 SQL 里 `WHERE` 必须先于 `ORDER BY ... LIMIT` 执行是同一个道理；数据库引擎把过滤条件尽量提前到存储层执行，叫**谓词下推**——本项目把 doc_id 条件直接下推给 Chroma（`where={"doc_id":{"$in":[...]}}`），而不是捞回来再滤。

**本项目里的样子**：向量通道由 Chroma where 下推天然正确；BM25 是自己维护的内存数组，正确写法是在构造候选下标时就加 `doc_id in scope` 再让 BM25 排序取 top_k，这条由 4 个专门的测试（范围外更强匹配被忽略、先过滤再 top_k、未知 id、空列表）钉死。延伸坑：向量库只负责"最近邻"不负责"够不够相关"，所以空范围（空列表）在语义上被归一为全库，而不是"返回低分近邻"或"返回空"。

## 十三补三、通用知识兜底与接地降级（Day 14）

### 81. 接地降级（Grounding Fallback）⭐
**大白话**：系统坚持"先查资料再说话"，但翻遍书架确实没有时，不是永远把用户晾在那儿，而是经用户**显式同意**后允许模型"凭自己肚子里的墨水"答一次，并在答案开头大字标注"这不是书本上说的，自己核实"。关键词有两个：**接地优先**（检索流程必须照跑一遍，授权不是跳过检索的按钮）与**显式降级**（系统不自动开这个口子，每次都要用户亲手点）。它和"降级 / Degraded"是两码事：Degraded 是部分工具故障但答案照给、质量可能打折；Grounding Fallback 是证据客观为零时有控制地切换到非接地答案。

**本项目里的样子**：Agent 零证据 reject 气泡出现「🧠 用通用知识再答」按钮，点击以 `allow_general=true` 重发，服务端**重跑完整 ReAct**（范围圈选照常），仍零证据才切 `GENERAL_KNOWLEDGE_PROMPT` 答 `mode="general"`；检索管线故障（error 支）时按钮不出现、开关不响应——故障不能被措辞成"查过了没有"。

### 82. 通用知识兜底（General Knowledge Fallback）与 Per-Query 授权 ⭐
**大白话**：模型训练时吃下的公开常识叫**通用知识**（怎么做红烧肉、HTTP 状态码含义），与从用户知识库实时检索来的**接地证据**相对。兜底即用通用知识回答库外问题。**Per-query 授权**指同意只附着在"这一次请求"上——不是设置页里的永久开关，不写 cookie/本地存储，服务端也不记会话；下一个问题默认仍是"只许引用知识库"。这是隐私与信任的最小授权原则：权限随请求生、随请求灭。另外答案首行强制免责声明，且由**服务端后置补齐**（模型没写就代码补），不靠提示词自觉——提示词管大概率，代码管 100%。

**本项目里的样子**：`ChatRequest.allow_general: bool = false`（仅 `/api/agent/query` 接线，RAG 两端点收到直接忽略并有测试锁）；`AgentChatResponse.mode` 新增 `general` 枚举值（sources=[]、steps 保留本轮检索轨迹）；常量 `GENERAL_DISCLAIMER` 是声明唯一真值；前端同气泡复用重试骨架（不新增用户消息），琥珀色「GENERAL」徽标与金色 REJECT 分家，general 态不渲染来源卡。新增字段/枚举全带默认值，老请求行为逐字节不变。

## 十三补四、Agent 实时进度 SSE（Day 16）

### 83. 进度事件流（Progress Events）与事中可观测性 ⭐
**大白话**：进度条有两种——一种是**假进度**（一条走到头的动画条，实际到哪一步全靠猜），一种是**真进度**（系统每干完一步就喊一声"我在查 XX、查完了、查到 3 条"）。后者把"事后才能看的执行日志"变成"边执行边推送的事件流"，专业说法叫**实时可观测性（Real-time Observability）**。长等待的焦虑主要来自"不知道它活着没、在忙什么"，真进度直接消掉这个不确定性。

**本项目里的样子**：`run_agent` 新增可选异步回调 `on_event`，四类内部事件经 `POST /api/agent/stream` 推给前端：`phase`（正在分析问题/思考下一步/组织最终答案）、`tool_start`（工具执行**或缓存重放前**，查询词即刻上屏）、`tool_end`（完整 AgentStep，ok/empty/error 三态）、`done`（终态整包，与一次性 /query 同构）。关键纪律：服务层只认一个普通回调，完全不认识 SSE/HTTP（不传回调时老契约零变化）；业务故障（工具全失败等）依然收敛进 `done.mode=error`，只有编排层逃逸异常才发 `error` 事件——**故障要分类，但通道要收敛**。

### 84. 任务桥接与取消传播（Task Bridge / Cancellation Propagation，asyncio.Queue）⭐
**大白话**：干活的人和往外喊话的人是两个角色，中间放一根**传送带**（队列）：干活的把事件扔到传送带上，喊话的从传送带上取了再发给浏览器。浏览器提前走了（点了停止/关了页面），喊话的要回头喊一嗓子"别干了"——这声"别干了"一路传到干活的人那里，就叫**取消传播**。协作式取消只能在"喘口气"的点位（await）生效，已经发出去的那趟远程车叫不回来，但下一躺活儿肯定取消。

**本项目里的样子**：路由层 `asyncio.create_task(drive())` 跑 Agent，事件经单个 `asyncio.Queue` 桥接给 SSE 生成器（与 Day 12 同步流的"worker 线程 + 双 queue"不同：纯 async 两端用任务+单队列即可，别套旧方案）；客户端断连时生成器在 `finally` 里 `task.cancel()`，CancelledError 抛在 run_agent 当前 await 处，后续轮次的 chat/工具上游调用不再发出。测试进度事件时不用起服务——回调就是 `events.append`，直接断言事件列表的顺序与载荷。

### 85. 哨兵对象（Sentinel）与面向用户/面向运维的错误信息分层 ⭐
**大白话**：**哨兵（Sentinel）**是队列里用来表示"散会了"的特殊记号。要用一个内存里独一无二的对象（`object()`），而不是 `"done"` 这种字符串——万一路上真传来一个叫 done 的业务消息，散伙饭就提前开了。另一条工程常识是错误信息要**分层**：给用户看的做减法（短、稳、不露堆栈），给运维看的做加法（完整异常类型、入参现场、可检索），两边各取所需，不能混成一份。

**本项目里的样子**：drive 任务在 `finally` 里必投哨兵，SSE 生成器取到哨兵即退出，保证正常/异常/取消三条路径连接都能干净关闭，不会挂死。错误分层上：工具失败的短因限 120 字走 AgentStep.error 上屏（前端红色副行），完整原因经 `logger.warning("...tool=%s args=%s reason=%s")` 落服务端日志（pytest 用 `caplog` fixture 断言）；用户知道"哪步失败了"，运维能复盘"为什么失败"。

| 接地 / Grounded Generation | 生成必须基于检索证据、无证据拒答；本项目代码工具强制先检索再生成 ⭐ |
| 执行轨迹 / Agent Steps | Agent 把每步工具调用（工具/入参/结果数/缓存/状态）摊开给用户看，黑箱变玻璃箱 ⭐ |

| 降级 / Degraded | 部分工具失败但答案照给，显式标"可能不完整"，对应部分失败 Partial Failure ⭐ |
| 接地降级 / Grounding Fallback | 检索确实没有时，经用户显式同意才用模型自有知识作答，且重检不跳过 ⭐ |
| Per-Query 授权 | 同意只活在当次请求里（allow_general），无状态不残留，默认关闭 ⭐ |

| LangGraph | 构建 Agent 工作流的框架 |
| FastAPI | Python Web 框架，写 API 用的 |

| 装饰器 | @开头给函数挂能力的语法 |

| SSE | 服务器推送，用来做流式输出（本项目 POST /api/chat/stream ⭐） |
| lifespan | 应用开业/打烊时执行逻辑的机制 |
| 分层与依赖注入 | 按层组织、依赖由外部递进来 |
| venv | 项目级虚拟环境，隔离依赖 |

| 同步→异步桥接 | worker 线程迭代同步流 + 双队列传话给 async 侧；清理放 finally ⭐ |
| 429 / 指数退避 | 限流要等 1s→3s 再试；401 认证错立即失败不重试；业务失败 mode=error/HTTP 200 ⭐ |
| 双闸校验 | 后端 Pydantic max_length 硬闸（422，绕不过）+ 前端 maxlength 软闸（只管用户输入） ⭐ |
| OOXML / .docx | Word 新格式本质是 zip+XML，python-docx 可解析；老 .doc 是二进制，不支持 ⭐ |
| 灌库 Seeding / 幂等 | 批量导入初始语料；同名跳过，重跑结果不变（app.scripts.seed）⭐ |
| 批量上传/任务队列 | 前端多文件入队、串行调单文件接口，单文件失败不拖累整批 ⭐ |

| 检索范围过滤 | 请求带 doc_ids 白名单，只在指定文档内检索；无状态随请求携带，空=全库，RAG/Agent 同机制 ⭐ |
| 过滤先于 Top-K / 谓词下推 | 范围条件在候选预筛阶段生效（Chroma where 下推、BM25 先滤候选再排序），先取 top_k 再滤会被范围外高分占光名额 ⭐ |
| 进度事件流 / 实时可观测性 | Agent 每步执行（轮次/查询词/成败）经 SSE 边干边播，黑盒等待变"执行直播"（/api/agent/stream）⭐ |
| 任务桥接 / 取消传播 | asyncio 任务 + asyncio.Queue 桥接执行与 SSE；断连 finally 里 cancel，后续轮次上游调用不再发出 ⭐ |
| 哨兵 Sentinel | 队列收尾用的唯一对象（object()），finally 必投，防止连接挂死；别用业务字符串 ⭐ |
| 错误信息分层 | 用户侧短因（≤120 字）+ 运维侧 warning 全因日志；caplog 可断言 ⭐ |
