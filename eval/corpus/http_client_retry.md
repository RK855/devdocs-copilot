# HTTP 客户端重试与超时

## 超时设置

每个外部请求都必须设置超时。没有超时的请求在上游卡死时会一直挂起，最终耗尽连接池。超时应分开设置连接超时与读取超时：连接超时短（如 3 秒），读取超时按业务（如 30 秒）。

```python
httpx.Client(timeout=httpx.Timeout(connect=3, read=30, write=10, pool=5))
```

## 重试策略

只重试可恢复的错误：连接失败、超时、502/503/504、429。不要重试 400/401/403/404/422，这些是客户端问题，重试无意义还增加负担。

采用指数退避加抖动：第 1 次等 1 秒，第 2 次等 3 秒，加随机抖动避免同时重试造成雪崩。重试次数通常 1 到 2 次，再多会放大延迟。

## 幂等性

重试的前提是操作幂等。GET、PUT、DELETE 天然幂等；POST 创建需要幂等键或客户端去重，否则重试可能产生重复订单。

## 熔断与降级

上游持续失败时应快速失败，而不是继续排队重试。熔断器在错误率超过阈值后打开，一段时间后放少量请求探测。降级策略包括返回缓存、返回兜底文案、关闭非核心功能。

## 限流与并发控制

用信号量限制同时请求上游的数量，避免把对方打挂。批量场景控制并发度，不要一次发起上千请求。

## 错误分类

把异常分成可重试与不可重试两类，分类逻辑集中在一处，避免每个调用点各写一套。日志要记录状态码、响应体摘要、耗时、重试次数。

## 连接池

复用客户端实例，利用连接池减少握手开销。客户端应在应用生命周期内复用，而不是每个请求新建。关闭应用时统一关闭客户端。

## 流式请求的特殊性

流式响应的重试很麻烦：已经开始输出后不能重试，否则会重复内容。只能在首包前失败时重试。因此流式链路通常在首包前完成所有可能失败的准备（鉴权、参数校验、上游首包）。

## 同步客户端与异步框架

在异步框架中使用同步客户端会阻塞事件循环。解决方案是放入线程池，但要保证客户端的创建、使用、关闭在同一个线程内完成。某些 SDK 的流对象绑定创建线程，跨线程关闭会导致连接泄漏。

## 常见坑

- 不设超时
- 重试 4xx
- 无退避的重试风暴
- 重试非幂等写操作
- 每个请求新建客户端
- 流式响应中途重试
