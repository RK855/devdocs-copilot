# CI/CD 流水线

## 持续集成

每次推送代码自动运行检查：格式化、静态检查、单元测试、构建。目标是在合并前尽早发现问题，减少人工回归成本。CI 失败应阻断合并。

## 常见步骤

1. 检出代码
2. 安装依赖（带缓存）
3. 运行 lint 与类型检查
4. 运行测试
5. 构建产物
6. 上传制品或镜像

步骤顺序从快到慢，快速失败能节省时间。

## 缓存

依赖缓存能显著缩短流水线。缓存键通常包含依赖文件哈希，依赖不变时复用。缓存污染可能导致奇怪失败，必要时提供清除手段。

## 测试分层

单元测试秒级完成，放在每次推送；集成测试与端到端测试较慢，可以放在合并前或定时任务。真实外部 API 的测试要跳过或用密钥门控，避免在公共 CI 环境泄露密钥。

## 环境与密钥

CI 密钥存在平台提供的 secrets 中，不写在仓库里。PR 来自 fork 时通常不注入密钥，需要相应跳过集成测试。

## 持续交付与部署

构建产物应带版本号或提交哈希，保证可追溯。部署流程要可回滚，失败时自动停止。生产部署通常需要人工审批。

## 制品管理

构建一次，多处部署。不要在部署阶段重新构建，否则同一版本在不同环境可能不一致。制品仓库保存产物与元数据。

## 流水线速度

超过十分钟的流水线会让人频繁打断工作。拆并行任务、缓存依赖、只跑受影响模块都能提速。测试本身也要保持快。

## 常见坑

- CI 只跑 lint 不跑测试
- 密钥硬编码在配置里
- 依赖不锁版本导致随机失败
- 构建与部署产物不一致
- 没有失败通知，问题长期无人处理
