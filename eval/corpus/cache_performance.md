# 缓存与性能优化

## 缓存的基本模式

缓存是用空间换时间：把计算结果或远程数据存起来，下次直接读取。关键问题是失效策略。常见模式：

- Cache-Aside：读时先查缓存，未命中查源并回填
- Write-Through：写时同时更新缓存与源
- Write-Behind：写先落缓存，异步刷回源

读多写少的场景适合 Cache-Aside，实现简单，缓存故障时退化为直查源。

## 缓存键设计

键要包含所有影响结果的维度：用户、租户、语言、版本、查询参数。漏掉维度会导致串数据，是缓存最危险的 bug。键长度要可控，长查询可以先哈希。

## 过期与淘汰

TTL 控制新鲜度，LRU/LFU 控制内存占用。TTL 太短命中率低，太长数据陈旧。对一致性要求高的数据，可以用“更新时主动删键”配合短 TTL 双保险。

## 缓存穿透、击穿、雪崩

- 穿透：查询不存在的数据，缓存永远不命中，每次都打源。解决：缓存空值（短 TTL）或布隆过滤器。
- 击穿：热点键过期瞬间大量请求打源。解决：互斥锁只让一个请求回源，其余等待。
- 雪崩：大量键同时过期。解决：TTL 加随机抖动，分批预热。

## 本地缓存与分布式缓存

单进程内存缓存最快，但多实例不一致，重启丢失。Redis 等集中缓存一致性好，但多一次网络往返。常见组合：本地缓存短 TTL + 集中缓存长 TTL。

## 异步与批处理

减少等待时间的另一个方向是并行化。多个独立外部调用用 `asyncio.gather` 并发；能批量查询的接口不要循环单查。N+1 查询是性能杀手，预加载或批量接口能显著降低延迟。

## 流式响应

对长文本生成，等待完整结果再返回会让首字节时间很长。流式输出先返回首包，用户感知更快，总耗时未必降低。要区分 TTFT（首字节时间）与总时长两个指标。

## 连接复用

HTTP 客户端应复用连接池，避免每次请求重新握手。数据库连接池同理。池大小要匹配并发量，过大会拖垮数据库，过小会排队。

## 性能度量

先测量再优化。关注 P95/P99 而不是平均值；区分 CPU、IO、网络瓶颈；用压测工具模拟真实并发。没有基线的“优化”往往只是把瓶颈挪到别处。

## 常见坑

- 缓存键漏维度导致数据串号
- 缓存大对象导致内存暴涨
- 缓存故障时没有降级路径
- 在请求路径里做全量刷新
- 优化了非热点代码
- 只测平均延迟不看长尾
