# 配置文件管理

## 格式选择

JSON 适合机器读写与接口传输，不支持注释；YAML 可读性好、支持注释与嵌套，但缩进敏感、解析器行为有差异；TOML 适合应用配置，语义清晰；`.env` 适合密钥与部署环境变量。

项目中常见组合：`.env` 放密钥与部署差异，`config.yaml` 放业务默认值，环境变量覆盖。

## 配置分层

配置应分层：代码内置默认值 → 配置文件 → 环境变量 → 命令行参数。优先级从低到高，后层覆盖前层。这样本地开发零配置可跑，生产用环境变量注入。

## 密钥与示例文件

仓库只提交 `.env.example`，列出所有变量名与说明，值留空或占位符。真实 `.env` 加入 `.gitignore`。首次启动时若检测到缺失，可以引导用户复制示例并填写。

密钥绝不能硬编码在代码或配置文件里。日志里也不要打印完整密钥。

## 解析与校验

配置读取后应立即校验：必填项是否存在、类型是否正确、取值范围是否合法。启动时失败比运行到一半失败好排查。用 Pydantic Settings 可以把环境变量映射成类型化对象，缺字段直接报错。

```python
class Settings(BaseSettings):
    api_key: str
    timeout: int = 30
    model_config = SettingsConfigDict(env_file=".env")
```

## 路径处理

配置中的相对路径要锚定明确的基准目录，通常是项目根或可执行文件所在目录。打包成可执行文件后工作目录会变化，用相对路径容易找不到文件。区分可写目录（数据、上传）与只读资源目录（内置文档、静态文件）。

## 环境隔离

开发、测试、生产使用不同配置。测试不应读取生产配置，避免误连真实数据库。可以在测试初始化时强制覆盖关键配置。

## 热更新

大多数配置修改后需要重启生效。支持热更新会增加复杂度与一致性风险，除非确有需求，否则保持重启生效更简单可靠。

## 常见坑

- 把 `.env` 提交到仓库
- 缺少默认值导致本地启动失败
- 用相对路径在打包后失效
- 环境变量名拼写错误却被静默忽略
- 配置项没校验，错误值到运行时才暴露
- 日志打印完整配置包含密钥
