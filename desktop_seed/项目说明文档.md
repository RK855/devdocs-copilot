# DevDocs Copilot 项目说明文档

> 技术文档智能问答助手 —— 基于 RAG + Agent 的 AI 应用

---

## 一、项目概述

### 1.1 项目是什么

**DevDocs Copilot** 是一个面向开发者的技术文档智能问答助手。用户上传技术文档（Markdown、TXT、PDF、Word（.docx）等）构建知识库，用自然语言提问，系统从文档中检索相关内容，结合大语言模型给出准确回答，并标注引用来源。

更进一步，系统支持 **Agent 模式**——AI 自主决定是查文档、生成代码示例还是解释错误信息，扮演"资深工程师助手"。

### 1.2 为什么做这个项目

- **市场需求大**：企业知识检索、开发者文档助手是 RAG 落地最多的场景
- **容易讲清楚**：面试时一听"技术文档智能问答"就能明白价值
- **技术栈完整**：覆盖后端 API、向量数据库、LLM 应用、Agent 核心技能
- **有量化空间**：自带评测体系，用数据展示效果提升

### 1.3 目标用户

- 开发者：快速查找技术文档
- 技术团队新人：快速上手内部文档
- 学习者：对着文档提问，比自己硬读效率高

|--------|--------------|----------------------|

| 协议 | OpenAI 兼容 | OpenAI 兼容 |
| 费用 | 当前免费 | 当前免费 |

**已实测验证的事实：**

- Agnes 国际站可**裸连**访问（无需常开代理；超时先重试，必要时再开代理）

- **全链路零 API 费用**

### 2.3 弃选方案备忘（面试可讲选型过程）

| 方案 | 弃选原因 |
|------|---------|
| DeepSeek / GLM 聊天 | Agnes 上下文更大（512K）、编码专项更强、同为免费 |

## 五、核心数据流转

### 5.1 文档摄入（Ingest）

```
用户上传文档
  → 校验通过（类型/大小/非空）后，源文件以 {doc_id}_文件名 存入 uploads/
  → document_parser 解析内容（md/txt 编码兜底、pdf 逐页、docx 段落+表格）
  → 文本切分（约 500 字符/块，50 字符重叠）
  → 调用硅基流动 bge-m3 批量生成 1024 维向量
  → 向量 + 原文 + 元数据（doc_id/文件名/块序号/页码/source）存入 Chroma
  → chunk 原文同步写入 BM25 内存索引
完成，文档可被检索
```

**语料两视图（会话划分，与入库渠道无关）**：服务启动时对"当时已在库的文档"拍一次快照（会话基线，纯内存不持久化）——

- **语料库**：会话基线内的文档，即本次启动时已在库的全部语料；
- **我的上传**：基线之外的文档，即本次服务启动之后新上传的文档。

服务重启后基线重新拍照，上一轮"我的上传"里的文档自动沉淀进"语料库"。两视图只是列表口径，不影响检索（检索范围由视图跟随或「选文档」显式勾选决定）。

### 5.2 问答（Query）

```
用户提问
  → 问题向量化（bge-m3）
  → 两路并行检索：
      向量检索 Top-20（Chroma）
      BM25 检索 Top-20（关键词）
  → RRF 融合 → Top-10
  → Rerank 精排 → Top-5
  → Top-5 片段 + 问题 + 系统提示词构建 Prompt
  → 调用 agnes-2.5-flash 生成回答
  → 返回：回答 + 引用来源（文档名/片段/分数）
```

### 5.3 Agent 问答

用户在顶栏手动切到 AGENT 模式后，系统基于 ReAct 循环（思考 → 行动 → 观察）工作：

1. Agent 思考问题需要什么工具
2. 调用工具：`search_docs` / `generate_code_example` / `explain_error`（可一轮并行调多个）
3. 观察结果，判断是否足够回答
4. 足够则综合所有结果给出最终回答，否则继续循环（最多 5 轮，超限强制收尾）

**Day 16 实时进度（SSE）**：浏览器走 `POST /api/agent/stream`，上述循环的每个阶段实时推送给前端——`phase`（正在分析问题/思考下一步/组织最终答案）→ `tool_start`（在查什么词/做什么任务）→ `tool_end`（成功几条/零命中/失败短因）→ … → `done`（完整结果，与一次性 `/query` 同构）。等待期间用户看到的是"执行直播"而非转圈动画，并可随时点「停止」中断后续轮次；`/api/agent/query` 保留给 API 客户端与 eval 评测脚本。

## 六、关键技术原理

### 6.1 混合检索为什么比单一检索好

| 检索方式 | 擅长 | 不擅长 |
|---------|------|--------|
| BM25 | 精确匹配、专业术语、代码标识符 | 语义相似但用词不同 |
| 向量 | 语义相似、同义表达 | 精确关键词、数字 |

两者优势互补。**RRF 融合**：按排名打分 `score = 1/(rank + 60)`，多路分数相加后重排——把多个排名合并成一个的常用方法。

### 6.2 Rerank 的作用

向量相似度是"粗筛"（快但不够准）；Reranker 逐个比较问题与候选文档的相关性（慢但准）。两阶段思路：粗排（向量+BM25 → RRF 取 10，召回高）→ 精排（cross-encoder 逐对打分取 Top-5，更准）。

**bi-encoder vs cross-encoder**：embedding 模型把问题和文档各自编码成向量再算余弦——问题与文档在编码时互不可见，快但损失交互信息；rerank 模型把"问题 + 候选文档"拼起来一起过 Transformer，逐 token 交互后输出相关性，准但每对都要算一次，所以只能精排小候选集。

**F7 实测补充（2026-09-26）**：cross-encoder 只判问答对相关性、不做"文档归属"约束——当知识库里有别的框架/通用规范的近邻文档（如 Flask 段落字面也能回答 FastAPI 问题）时，它可能把跨文档的近邻块排到前面。工程对策：二次证据门（阈值 0.02）解决"无答案"问题；文档级归属约束留作后续演进。

### 6.3 Agent ReAct 模式

ReAct = Reasoning + Acting。Agent 循环执行 思考 → 调用工具 → 观察结果 → 再思考，直到能回答。能力更强（多步推理、多工具），代价是更慢、更贵、更易出错——所以需要最大步数护栏、工具异常兜底与接地约束。

| POST | `/api/agent/query` | F8 Agent 问答（ReAct 自主多轮检索） | `{ answer, sources, mode, degraded, response_time, steps }`，`mode` 为 `agent`/`reject`/`error`/`general`（Day 11：error=检索管线全程故障或主 LLM 致命异常，HTTP 仍 200，answer 为固定文案；Day 14：general=用户显式授权且服务端重跑 ReAct 仍零证据时以通用知识作答，sources=[]、steps 保留、answer 首行为固定免责声明）；`steps: [{ step, tool, arguments, result_count, cached, status, error }]`，`status` 为 `ok`/`empty`/`error`（并行调用共用同一 step 编号，缓存命中 `cached=true`）；`degraded=true` 表示部分工具失败但仍给出答案。请求体同为 `{query, doc_ids?}`（Day13++续：范围对 Agent 每一轮 search_docs 都生效）加 Day14 可选 `allow_general: bool=false`（仅当次请求有效、无状态；true 不跳过检索，仍 reject 才降级；故障支与有证据时不生效；RAG 两端点即使携带也忽略） | ✅ |
| POST | `/api/chat/stream` | F9 RAG 流式问答（SSE，`text/event-stream`） | 事件帧序列（`event:`+`data: JSON`，不转义中文）：`meta{mode,response_id}` → `sources[SourceOut 五字段]` → `delta{text}`×N → `done{response_time}`；拒答为 meta(reject)+整一条拒答 delta+done（零 LLM/无 sources）；故障发 `error{code,message}` 后不发 done，code 三枚举：`retrieval_failed` / `llm_unavailable`（首字前；Day 13：认证错误沿用此 code，message 换成认证文案）/ `stream_interrupted`（有 delta 后，已吐内容保留）。请求体同为 `{query, doc_ids?}`，query 要求 1~2000 字（空或超长 422），doc_ids 语义同 /query（Day13++续）；客户端可随时断连（AbortController），服务端随即关闭上游 LLM 流 | ✅ |
| POST | `/api/agent/stream` | Day 16 Agent 流式**进度**问答（SSE，`text/event-stream`）；终答仍为整包、非逐字 | 请求体同 `/api/agent/query`：`{query, doc_ids?, allow_general?}`，空白/超长 422。事件帧：`phase{phase:"thinking",round}`（每轮 chat 前）→（`tool_start{step,tool,arguments,cached}` → `tool_end{完整 AgentStep}`）×N → `phase{phase:"answering"}`?（超步收尾/空正文补呼/general 兜底三处终答前）→ `done{完整 AgentChatResponse}`（与 /query 同构，含 agent/reject/error/general 全部业务终态）；仅编排层逃逸异常才发 `error{code:"stream_interrupted"}`（不新增 code、不发 done）。客户端断连（AbortController）后服务端 cancel 执行任务，后续轮次上游调用不再发出；前端实时轨迹卡+停止/重试 | ✅ |

### 9.1 指标

| 指标 | 含义 |
|------|------|
| Recall@5 | 前 5 个结果命中相关文档的比例 |
| MRR | 第一个正确结果排名倒数的平均值 |
| 引用准确率 | 回答中真实相关的引用占比 |

### 9.2 用例与对比（F7 已落地 ✅）
